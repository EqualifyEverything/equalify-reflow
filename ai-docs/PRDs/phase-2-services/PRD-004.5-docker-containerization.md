# PRD-004.5: Docker Containerization for Monolith Application

## Overview
**Epic**: Docker Containerization & Unified Development Environment
**Phase**: 2.5 - Infrastructure Enhancement (between PRD-004 and PRD-005)
**Estimated Effort**: 0.5 days (4 hours)
**Dependencies**: PRD-004 (API Endpoints) ✅
**Parallel**: ❌ Must complete before PRD-005

## Problem Statement

The current development workflow creates **environment fragmentation**:
- **Infrastructure (Redis, LocalStack)**: Running in Docker containers
- **Application (FastAPI)**: Running on host machine with `uv run uvicorn`
- **Network Resolution**: Services use Docker hostnames (`redis:6379`, `localstack:4566`) which fail from host context
- **Configuration Complexity**: Two sets of connection strings needed (Docker vs localhost)

This causes:
1. **Developer Experience Issues**: Complex setup requiring manual service coordination
2. **Environment Parity**: Development (host-based) ≠ Production (container-based AWS ECS)
3. **Debugging Challenges**: Network issues, hostname resolution failures
4. **Onboarding Friction**: New developers must understand dual-environment setup

**Architecture Alignment**: The application is a **monolith with background workers** that should run as a **single containerized process** alongside its infrastructure dependencies.

## Solution

Containerize the FastAPI monolith application so the entire stack runs in Docker Compose with unified networking. This achieves:
- ✅ Single `make dev` command starts everything
- ✅ Consistent hostname resolution across all services
- ✅ Matches production deployment pattern (AWS ECS containers)
- ✅ Simplified developer onboarding
- ✅ Hot-reload preserved for development iteration speed

## Technical Decisions

### Why Keep Docker Compose (Not Just Dockerfile)?
- **Orchestration**: Coordinates Redis, LocalStack, FastAPI together
- **Environment Parity**: Matches AWS ECS multi-container task definitions
- **Developer Experience**: Single command starts entire stack

### Why Hot-Reload in Containers?
- **Iteration Speed**: No rebuild cycle for code changes
- **Developer Productivity**: Instant feedback on changes
- **Best of Both Worlds**: Container isolation + fast development

### Why Multi-Stage Build?
- **Production Optimization**: Smaller image, no dev dependencies
- **Development Experience**: Full tooling for debugging
- **Security**: Production runs with minimal attack surface

## Architecture Alignment

**Monolith Pattern**: This change reinforces the monolith architecture:
- ✅ Single container runs entire application (FastAPI + future background workers)
- ✅ Shared configuration and code in one process
- ✅ Unified logging and monitoring
- ✅ Matches AWS ECS deployment model

**NOT Creating Microservices**: We're containerizing the monolith, not splitting it into separate services. Background workers (PRD-005+) will run as threads/tasks within the same container.

## Risk Mitigation

| Risk | Impact | Mitigation |
|------|--------|------------|
| Hot-reload doesn't work | Low dev velocity | Volume mount permissions, test thoroughly |
| Network issues between containers | API can't reach Redis/S3 | Use Docker DNS, test connectivity |
| Container build is slow | Developer frustration | Multi-stage build, layer caching |
| Existing tests break | Development blocked | Minimal config changes, validate incrementally |
